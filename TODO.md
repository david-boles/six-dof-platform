## 1. Architecture (decide first — everything else builds on this)
Context (David): board is a Seeed XIAO ESP32C6 (4 MB flash, 512 KB SRAM; USB-C appears to go straight to the chip's native USB-Serial-JTAG: probe-rs uses it with no external probe and the Seeed wiki lists no USB-UART chip, not yet confirmed with `lsusb`). Standalone operation (no laptop) is probably **not** needed. No host program (1.2). History retention: undecided.
Long-term (David): the stand exists to characterize a monocopter, likely with an ESP32-C6 flight controller that will need wireless telemetry (and probably OTA updates); maybe closed-loop full-system HIL simulations on the stand. The comms stack should be reusable there.

- [x] **1.1** (decided: **transport-agnostic stack, USB first**; USB's lower latency suits HIL. Wi-Fi later for the monocopter. BLE not for data, but maybe as a control channel for Wi-Fi setup: AP vs. STA, SSID/password) Transport from the ESP32-C6 to the browser. Options considered:
  - USB (native USB-Serial-JTAG CDC-ACM serial port), read by a host program or directly by the browser (Web Serial: Chrome 89+, Firefox 151+, no Safari)
  - Wi-Fi (`esp-radio`, `embassy-net`), WebSocket served by the ESP
  - RTT via the debug probe, read by a host program using the `probe-rs` library
  - Bluetooth LE (`esp-radio` `ble` feature + `trouble-host`; C6 has BLE 5 only, no Classic/SPP), read by a host program (`btleplug`) or the browser (Web Bluetooth: Chrome, not enabled by default on Linux; no Firefox/Safari)
- [x] **1.2** (decided 2026-11-13: **no host program; static Rust/WASM page talking to the device over Web Serial**) (needs a secure context: `localhost` or HTTPS). Consequences: history lives in the browser (memory/IndexedDB), recording stops when the tab closes, one tab owns the port, calibration best stored on the device. HIL (later) may still want a native program; the protocol crate keeps that open
- [x] **1.3** (decided 2026-11-13: **Leptos** (CSR; built by `cargo xtask` into a single HTML file instead of Trunk, see 4.0) for UI/forms; **`three-d`** on a Leptos-owned `<canvas>` for 3D; **self-drawn canvas plots** for live data (revisit uPlot interop for interactive history; graphs on hold, 4.3). 250 Hz data goes into a ring buffer and canvases redraw once per animation frame; Leptos signals carry only slow-changing state) Web stack. Alternatives considered: Dioxus, Yew, egui/eframe (immediate-mode, canvas-drawn; same code runs native). 3D: three.js via JS interop vs. Rust on WebGL2 (`three-d` 0.19 on a Leptos-owned `<canvas>`: `glow::Context::from_webgl2_context` → `three_d::Context::from_gl_context`; glTF loading, PBR, orbit camera, `CpuMesh::arrow`; uses glow 0.17). Plots: uPlot via interop vs. Rust canvas plotting. egui: David hasn't enjoyed it. gpui (Zed): ruled out for now (web backend `gpui_web` is unpublished, git-only, nightly-only via `parking_lot/nightly`, wasm threads; no hook for custom GPU/3D rendering)
- [x] **1.4** (decided 2026-11-13: **`postcard-rpc`**; implemented in `protocol/`, see 2.1/4.0) Wire protocol: message types shared between firmware and browser (`no_std` crate `protocol/` with `serde` + `postcard`, COBS framing on byte streams), designed to be transport-independent. Dropped readings are detected from gaps in `Readings::timestamp_us`. `postcard-rpc`: endpoints = request/response, topics = streams; server generic over transports, has an `embedded-io-async` COBS server. Released 0.12.1 needs `embassy-executor` 0.9 (we use 0.10), so we use **David's fork** `https://github.com/david-boles/postcard-rpc`, branch `0.12.1-embassy-executor-0.10` = `v0.12.1` + executor 0.10 support only, pinned to commit `301d138` (2026-11-18); the fork's README describes its changes. Drop the fork once a release supports executor 0.10. Alternative for later telemetry: MAVLink (`mavlink` crate). Browser side: the host client compiles for wasm (has wasm-specific `WireTx`/`WireRx`/`WireSpawn` traits and a WebUSB transport, which doesn't fit the C6's fixed CDC-ACM interface) → write a Web Serial wire (COBS) ourselves; `web-sys` Serial bindings need `--cfg=web_sys_unstable_apis`. Avoid `get_schema_report()` and nonzero `subscriber_timeout_if_full` in wasm: they use `tokio::task::spawn` / `tokio::time`, which need a tokio runtime (not present under `spawn_local`)
